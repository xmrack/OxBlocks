JSON API

Every endpoint below is a GET and needs no key, no header and no session. Responses are compatible field-for-field with onion-monero-blockchain-explorer wherever an endpoint exists in both, so a client written against that explorer works here unchanged.

Each endpoint below carries a runnable curl line. They refer to $OXBLOCKS rather than a hostname: set it to this explorer's base URL, scheme included, and the examples run as written. No URL is printed on this page on purpose — an explorer is often read over Tor, and a page that names a host gives the reader something to click that leaves it.

The envelope

Every answer this API produces is wrapped in one of three shapes. 

{"data": { … }, "status": "success"}
{"data": {"title": "Cant find tx: …"}, "status": "fail"}
{"data": null, "message": "…", "status": "error"}

fail means the caller asked for something this explorer will not answer: an argument that will not parse, a height past the tip. error means this explorer or its daemon could not answer. Error messages are deliberately vague about internals: an unreachable daemon reports “the explorer could not reach its daemon” rather than naming the address it failed to reach.

Status codes

The HTTP status says the same thing as the envelope. This is the one place the API departs from upstream, which answers 200 to everything and leaves the outcome to the status member alone. A client that reads status is unaffected.

CodeMeaning
200The answer is in data.
400The argument is not one this explorer reads, or a limit is over its cap.
404The argument was well formed and the chain does not hold it.
500A bug here.
502The daemon could not be reached, or answered with something unusable.
503This deployment cannot serve the endpoint, because of how its daemon is built or configured.

Keys are sorted alphabetically, recursively, throughout. Enveloped responses carry Content-Type: application/json and Access-Control-Allow-Origin: *, and are compressed with gzip, deflate or brotli if the request offers one.

Three answers are not enveloped, because they are produced above this API rather than by it: a request that outlives its deadline is a bare 504, a request body over the limit is a 413, and a panic caught in a handler is a 500. All three are text/plain and carry no status member. Every one of them still carries the security headers.

HEAD is served wherever GET is, with the body stripped. Any other method gets a bare 405 with Allow: GET,HEAD and no Access-Control-* headers — there is no preflight handler, so a cross-origin request that triggers one will fail. Simple cross-origin GETs work.

How arguments are read

Arguments are read as given. A height is decimal digits, a hash is 64 hex characters of either case, and a postfix is hex. Anything else is a 400, and so is a page or limit that is not a plain number. Nothing is stripped or repaired first, so /api/block/1,23 is refused rather than answered as block 123.

GET/api/version

The API revision and the daemon's version string. api is (major << 16) | minor; these are the 1.3 shapes, so it reads 65539. The three git_* fields are always empty — oxblocks embeds no build metadata, and the keys exist only because clients index them. oxblocks_version is not an upstream key: a client should not have to infer which implementation it is talking to from the absence of a commit hash.

One caveat worth knowing: under --restricted-rpc monerod falsifies several get_info fields rather than omitting them, and version is one of them — it becomes the empty string. So an empty monero_version_full means either a restricted daemon or one that reported no version, and this response cannot tell you which. oxblocks expects an unrestricted daemon.

/api/version

curl -s "$OXBLOCKS/api/version"

GET/api/networkinfo

Twenty-six fields of chain and node state. Three of them are easy to get wrong: difficulty and cumulative_difficulty are JSON strings, because 128-bit values do not survive a double; status is a boolean field of data, which is a different thing from the envelope's "status": "success"; and tx_pool_size_kbytes carries bytes despite the name, which is upstream's bug and would break every consumer if corrected here.

The string typing of the two difficulty fields is not decoration: a JSON parser backed by doubles loses integers above 253, and cumulative difficulty passed that long ago. The same hazard applies to the numeric fields that can grow large — hash_rate is emitted as a JSON number and saturates at u64::MAX rather than wrapping, so a double-based client should read it as a string from the raw body if the exact value matters.

/api/networkinfo

curl -s "$OXBLOCKS/api/networkinfo"

GET/api/block/<height|hash>

One block and every transaction in it, coinbase first. The argument is a height if it is eight characters or fewer, a block hash if it is exactly 64 hex characters, and rejected otherwise — the eight-character bound is upstream's, and it bounds the text rather than the value.

Returns a block object. Note that size is an integer here and a float in /api/transactions, because upstream holds it in two different C++ types.

/api/block/{{ sample_height }}

curl -s "$OXBLOCKS/api/block/{{ sample_height }}"

GET/api/rawblock/<height|hash>

The block exactly as monerod decoded it — the daemon's own json document, reparsed and re-emitted with its keys sorted. The reparse is not ceremony: monerod emits that document in declaration order, and forwarding the string verbatim would not match upstream byte for byte.

/api/rawblock/{{ sample_height }}

curl -s "$OXBLOCKS/api/rawblock/{{ sample_height }}"

GET/api/blocks/<start>/<end>

A range of blocks, inclusive at both ends, as an array of block objects. Ask for a window and take the one you meant, so the explorer never learns which block you wanted.

Capped at {{ max_block_range }} blocks per request. Upstream imposes no cap because it reads its own database; every block here costs the operator's daemon a call, so an uncapped range would let one request make millions of them. A wider range is refused rather than truncated.

/api/blocks/{{ sample_range_start }}/{{ sample_height }}

curl -s "$OXBLOCKS/api/blocks/{{ sample_range_start }}/{{ sample_height }}"

GET/api/transaction/<hash>

One transaction, with every ring resolved — each input lists its decoys with the height, one-time key and source transaction of each. This is the only endpoint that expands rings, because doing it costs a daemon call per input.

Returns a transaction detail object. Works for pool transactions too, which report block_height 0, confirmations 0, and the time they arrived rather than a block timestamp. 

curl -s "$OXBLOCKS/api/transaction/<hash>"

GET/api/rawtransaction/<hash>

The transaction exactly as monerod decoded it, keys re-sorted, with no interpretation of any kind. 

curl -s "$OXBLOCKS/api/rawtransaction/<hash>"

GET/api/transaction/private/<postfix>

Every transaction whose hash ends with the given hex postfix. The caller picks the one it wanted locally, so the explorer never learns which. Returns txs and missed_txs.

Rings are deliberately not expanded: inputs are listed with their amount and key image, and mixins is null. Expanding every ring of an anonymity set would be thousands of calls for a caller who wants one of them, and it can ask for that one through /api/transaction.

A postfix must be {{ min_postfix_len }} to {{ max_postfix_len }} hex characters, and must name a set large enough to hide in and small enough to serve: between {{ min_anonymity_set }} and {{ max_private_tx_matches }} expected matches. Both bounds are counts rather than lengths, so which lengths qualify moves with the size of the chain. GET/api/transactions?page=&limit=

A page of recent blocks with their transactions summarised, newest first.

ParameterDefaultMaximumNotes
page0—counts back from the tip
limit25{{ max_transactions_limit }}clamped, not rejected

The clamp is a divergence from upstream, which does not have one. A page here costs one header range, one call per block that holds transactions and one batched fetch; unclamped, a single request could reach a thousand blocks against the operator's daemon.

total_page_no is a second divergence: it rounds up. Upstream floors it, so a client that trusts the number stops one page early and never sees the oldest blocks.

/api/transactions?page=0&limit=5

curl -s "$OXBLOCKS/api/transactions?page=0&limit=5"

GET/api/transactions/recent

Every transaction from the last {{ recent_blocks }} blocks, plus the whole pool, in one answer and with no parameters. The point is that everyone asks for the same window, so asking reveals nothing about which transaction the caller cares about. Rings are not expanded, for the same reason as the private lookup.

The block window is bounded; the pool is not. During a mempool flood this is the most expensive endpoint here.

/api/transactions/recent

curl -s "$OXBLOCKS/api/transactions/recent"

GET/api/search/<height|hash>

Dispatches on the shape of the argument: a short number is a height, and 64 hex characters are tried as a block hash and then as a transaction hash. The matching object comes back with a title field naming which it is — "block" or "tx" — so a client can tell them apart without re-inspecting the fields.

Addresses are not searchable. Monero has no address index and cannot have one without scanning with a view key, which this explorer deliberately never asks for. 

curl -s "$OXBLOCKS/api/search/<height|hash>"

GET/api/feeestimate?grace_blocks=

The daemon's per-byte fee estimate. grace_blocks defaults to 10. fee and fee_per_kb report the same number: the estimate has been per-byte since 2019, and the second key kept its old name.

/api/feeestimate

curl -s "$OXBLOCKS/api/feeestimate"

GET/health

Liveness and cache occupancy. Not under /api and not enveloped — it answers a bare object. rpc_calls counts outbound calls to the daemon since start, which is not the same as cache misses: one batched fetch carrying forty hashes is forty misses and one call.

Deliberately says nothing about the daemon. A health check that fails when an upstream is slow turns one degraded dependency into an outage.

/health

curl -s "$OXBLOCKS/health"

Shared shapes

Three objects appear inside several responses. They are documented once here rather than repeated under each endpoint.

Block object

block_height, current_height, hash, size, timestamp, timestamp_utc, and txs, an array of transaction summaries with the coinbase first. current_height is the chain height, derived from this block's own depth rather than a second round trip.

Transaction summary

coinbase, extra, mixin, payment_id, payment_id8, rct_type, tx_fee, tx_hash, tx_size, tx_version, unlock_time, xmr_inputs, xmr_outputs.

mixin is the ring size, not ring size minus one, and is 0 for a coinbase. xmr_inputs and xmr_outputs are 0 wherever the amount is hidden, which the protocol does rather than this explorer. They carry real values in two cases: pre-RingCT transactions, where the chain itself is in the clear, and every coinbase — including a version 2 one, because a block reward is public by construction. A version number alone therefore does not tell you whether an amount is visible; rct_type and coinbase together do. unlock_time comes from upstream's devel branch; master does not emit it.

Transaction detail

Everything in the summary, plus block_height, confirmations, current_height, timestamp, timestamp_utc, inputs and outputs.

inputs is null — not [] — for a coinbase transaction, which spends nothing. Each input carries amount, key_image and mixins; mixins is itself null when the ring was not resolved, either because the endpoint did not ask or because the daemon refused the lookup. An empty array would claim the input has no ring members, which is a different statement.

Limits

Each of these is a deliberate divergence from upstream, which has none of them. Upstream reads its own database; every request here costs the operator's daemon network calls, so an unbounded request is a denial-of-service amplifier reachable by anyone who can make an HTTP request.

Deliberately absent

/api/outputs and /api/outputsblocks are not implemented, along with the /myoutputs, /prove, /rawtx and /checkandpush pages they belong to. They require pasting a secret view key into a server that could log it, and in the reference implementation they are the only routes that feed attacker-supplied hex into a deserializer. Omitting them removes the threat class rather than reimplementing it more carefully.

/api/emission is absent for a different reason: it needs either a background scanner or a full-chain scan, and this explorer keeps no state on disk.
