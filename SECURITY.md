# Security

## Reporting

Report vulnerabilities privately rather than through a public issue. Include
what you did, what happened, and what you expected.

## What this project claims

Narrower than "memory safe", and worth stating exactly:

* Every crate sets `#![forbid(unsafe_code)]`, enforced at compile time.
  `tools/check-unsafe.sh` fails the build if a crate stops inheriting it.
* No consensus code, no database handle and no C++ run in the web process. The
  explorer speaks to `monerod` over RPC and holds nothing else.
* `unwrap`, `expect` and slice indexing are denied in non-test code, so a panic
  reachable from a request is a build failure rather than a code review miss.
* Markup is generated by compile-time-escaped templates. Emitting an unescaped
  value requires writing `|safe`.

It does **not** claim the dependency tree is free of `unsafe`. It is not.
`cargo deny` runs in CI over advisories, licences, duplicate versions and source
registries; its advisory check reads the same RustSec database `cargo audit`
does.

## Deliberately absent

The view-key and transaction-pusher endpoints (`/myoutputs`, `/prove`,
`/rawtx`, `/checkandpush`, `/api/outputs`, `/api/outputsblocks`) are not
implemented. They require users to paste a secret view key into a server that
could log it, and in the reference implementation they are the only routes that
feed attacker-supplied hex into a deserializer. Omitting them removes the
threat class rather than reimplementing it more carefully.

## Deployment

`oxblocks` speaks plain HTTP and expects a TLS-terminating reverse proxy in
front of it. It has **no rate limiting**: `--max-concurrent` bounds how many
requests are served at once and `--max-inflight-rpc` bounds how many calls reach
the daemon, but nothing bounds requests per client. Rate limit at the proxy.

Point it at an unrestricted `monerod` on loopback. It needs no credentials, no
keys and no write access to anything; `deploy/oxblocks.service` removes every
capability it does not use.
